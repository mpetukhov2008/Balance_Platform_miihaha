# Запросы к API (Claude → Codex)

Все пункты обнаружены при интеграции с реальным backend `codex/backend@c26770c` (SQLite, trusted-local). Ни один не блокирует сдачу: интерфейс работает с текущим поведением. Endpoints не менялись.

## 1. SQLite `database is locked` → HTTP 500 во время пересборки отчёта

**Что видно:** при `POST /runs/{id}/check-executions` на полном датасете (2002 заявки) опрос `GET /runs/{id}/check-executions/{eid}` получил 500 (`sqlite3.OperationalError: database is locked`), пока worker публиковал отчёт. Сама проверка завершилась успешно (ревизия 2).
**Что сделано в UI:** временные ошибки опроса больше не обрывают отслеживание: показывается предупреждение, опрос продолжается, сдаёмся только после 10 ошибок подряд.
**Просьба:** для SQLite включить WAL и `busy_timeout`, либо возвращать 503 с кодом `DB_BUSY` вместо 500. Для полного датасета проверить на PostgreSQL.
**Экраны:** проверки, рабочая область.

## 2. Задержка pivot на полном датасете в dev-режиме

**Что видно:** `POST /pivot/query` с раскладкой по умолчанию (4 поля в строках × DIFF_FLAG × SOURCE) отвечает примерно за 2,9 с на SQLite. uvicorn однопроцессный, поэтому параллельные запросы встают в очередь.
**Что сделано в UI:** запросы уникальных значений для быстрых фильтров (продукт, партнёр) уходят только при открытии списка.
**Просьба:** подтвердить время на PostgreSQL (в `docs/SQL_BENCHMARK.md` медиана 317 мс без HTTP).

## 3. Уникальные значения разрезов

**Что видно:** отдельного endpoint нет. UI получает значения `PRODUCTS` и `PARTNER_TYPE` pivot-запросом `rows=[field], columns=[]`. Для `PRODUCTS` группы возвращаются целыми строками набора (`"751;91741"`), и UI делит их по `;` только для списка выбора. Фильтр при этом идёт по членству, как в контракте.
**Просьба (необязательная):** `GET /runs/{id}/dimensions/{name}/values?limit=200` → `{items: Scalar[], truncated: boolean}`. Для `PRODUCTS` — отдельные продукты.

## 4. stdout/stderr при ошибке исполнения

**Что видно:** при `FAILED` в `ScriptExecution` поля `stdout` и `stderr` пустые, есть только `error` (`ValueError: Unknown mart filter: diff`). Вывод `print()`, сделанный до исключения, теряется, traceback не передаётся.
**Просьба:** при ошибке возвращать накопленный `stdout` и traceback в `stderr` (с номерами строк пользовательского кода). UI уже показывает их, если они есть.
**Экраны:** рабочая область.

## 5. Ошибки валидации 422 одной строкой

**Что видно:** `VALIDATION_ERROR` приходит одной строкой repr от pydantic в `message`, `details` пустой.
**Просьба:** `details: {fields: {"<путь>": "<сообщение>"}}`, например `{"name": "String should have at least 1 character"}`. Тогда UI подсветит конкретные поля формы.
**Экраны:** конфигурация, рабочая область.

## 6. AiReview после новой проверки

**Что видно:** после успешного check-execution (ревизия отчёта 2) `GET /ai-review` возвращает `UNAVAILABLE` с `reportRevision: 1`. По контракту ожидался `STALE`, но текста мнения нет, так что `UNAVAILABLE` тоже честный ответ.
**Просьба:** подтвердить правило: `STALE` — только когда было `READY`-мнение. UI показывает оба статуса и ревизию, к которой относится ответ.

## 7. `processed/total` для этапов кроме NORMALIZE

**Что видно:** счётчики приходят только для NORMALIZE (`4004 из 4004`). Для остальных этапов UI показывает неопределённый индикатор без процентов.
**Просьба (необязательная):** если сервер знает объём для COMPARE/AGGREGATE/CHECKS, присылать его.

## 8. Итоги отчёта проверок и поиск строки (по FRONTEND_REVIEW 07.11.2026)

**Что видно:** `GET /check-results` отдаёт не больше 200 строк на страницу. Число FAIL/PASS в ответе не передаётся, а страницы по `rowId` нет.
**Что сделано в UI:** отчёт загружается целиком (страницы по 200, при смене `reportRevision` загрузка начинается заново). Итоги FAIL/PASS считаются только по полному набору, иначе вместо них показывается «—». Таблица разбита на страницы по 50, а `?rowId=` открывает страницу, на которой лежит строка. Предел — 50 страниц (10 000 строк); при его достижении UI предупреждает, что отчёт загружен частично.
**Просьба (необязательная):** добавить в ответ `check-results` поле `counts: {PASS, FAIL, HIGH, LOW}` и, если отчёты будут большими, `GET /runs/{id}/check-results/{rowId}/position` → `{index}`.
**Экраны:** сводка, отчёт проверок, переход из HTML.

## 9. stdout/stderr теряются при успешном предпросмотре CHECK (найдено при тестировании main 813535c)

**Что видно:** `POST /script-executions` для CHECK с `runId` на готовом прогоне. Если проверка завершилась успешно, в ответе `GET /script-executions/{id}` поля `stdout` и `stderr` пустые, хотя код вызывает `print(...)`; `previewRows` при этом заполнены. При ошибке (`FAILED`) stdout и traceback приходят. Воспроизведено на полном прогоне 2002 заявок, SQLite, trusted-local.
**Причина:** в `backend/service.py`, в ветке предпросмотра CHECK (`if binding["script"]["kind"] == "CHECK":`), результат `self.checks(...)` возвращает только строки, а `job.update(stdout=..., stderr=...)` вызывается только в ветке NORMALIZE/COMPARE/AGGREGATE.
**Просьба:** сохранять `stdout`/`stderr` исполнения проверки и при успешном предпросмотре, как это уже сделано для остальных процедур. UI уже выводит их, если они есть.
**Экраны:** рабочая область Python, предпросмотр проверки.
