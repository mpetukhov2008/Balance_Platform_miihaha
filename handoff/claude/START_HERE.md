### 3. Обязательные экраны

**Вход и сессия.** Вход, выход, текущий пользователь, понятная обработка истёкшей сессии. Регистрация и сложные роли не входят в минимальный объём. Пользователи подготавливаются сервером; реальные пароли не зашивать в приложение.

**Конфигурации и запуски.** Список своих конфигураций; создание и редактирование; выбор зарегистрированного датасета; выбор нормализации, сравнения и подготовки фактов; выбор набора проверок; редактируемые параметры; сохранение, повторный запуск. Для каждого скрипта доступны источники: рабочая область и размещённый в системе .py. Поля выбора отражают данные сервера, не произвольный локальный путь браузера. Когда полного data/ нет, показывать реально доступный набор samples как четыре заявки.

**Рабочая область Python.** Редактор кода, тип скрипта, параметры, сохранить, выполнить на выбранном контексте, stdout/stderr/диагностика, результат. Для проверки — выполнить на завершённом прогоне и включить результат в его единый отчёт. Не выполнять Python в браузере и не подключать Pyodide. Полный Jupyter и история версий не нужны; достаточно редактора, запуска и панели результатов. Показывать контракт и пример CHECK для проверки. Для остальных процедур описание входов/выходов и шаблон получать из каталога сервера: утверждённых сигнатур этих процедур в исходниках нет.

**Статус запуска.** Текущее состояние, этапы, количество обработанных элементов и общее число, если сервер его знает; журнал; ошибки. Процент не выдумывать. Опрос API примерно раз в секунду только пока запуск активен; прекращать при завершении и уходе со страницы. Из этапа — переход к текущему коду скрипта. Не открывать отчёт, пока он не опубликован сервером. Возврат на URL запуска после обновления страницы восстанавливает состояние из API.

**Сводка результатов.** Общее количество заявок, число заявок с любыми различиями, число со сменой решения, переходы решений, частые изменения. Эти показатели получать от API; не вычислять их суммированием всей pivot-таблицы. Отдельно показывать обнаруженное изменение внешних данных и результаты проверок. Изменения входа и стратегии могут совпадать; не представлять группы как непересекающиеся без ответа сервера.

**Сводная таблица.** Пользователь выбирает поля строк, колонок и фильтров и меняет порядок полей. Минимальная раскладка: иерархия атрибута в строках, DIFF_FLAG × SOURCE в колонках, сумма CNT в ячейках. Добавить CHANGE_TYPE, PATH и доступные серверу разрезы. Подойдут селекторы и кнопки перемещения; drag-and-drop необязателен. Должны работать фильтры продукта, партнёра и признака смены решения, если поля доступны. Пустые KEY/SUFFIX допустимы. Сводная строится поверх агрегированных фактов, а не всех строк сравнения.

Для первого варианта используй серверную pivot-выборку из API_CONTRACT.md и собственную таблицу с управляемой раскладкой. Это позволяет обойтись без зависимости от CDN и неопределённого API стороннего компонента. Если берёшь готовый компонент, сначала проверь его актуальную официальную документацию, лицензию, поддержку клика по агрегату и размер данных; не меняй серверный контракт. Не обещай конкретную совместимость непроверенной библиотеки.

**Переход к деталям.** Клик по ячейке открывает постраничный список уникальных заявок, с сохранением контекста фильтра. Далее карточка заявки: решения BEFORE/AFTER, разрезы, таблица атрибутов, фильтр отличий, PATH + ARRAY_KEY, исходное значение и бакет, четыре типа изменений. Выделить именно выбранный атрибут. По возможности добавить просмотр двух исходных JSON через отдельный запрос, не загружать их для всех заявок сразу. Различать отсутствие атрибута, null, false, ноль и пустую строку. Отсутствие определять по CHANGE_TYPE, а не по проверке truthy.

**Отчёт проверок.** Одна таблица с LABEL, SOURCE, ARGUMENT, CNT, TOTAL, METRIC, RESULT, CONFIDENCE и переходом к APP_IDS. LOW выделять слабо, а не ярко-красным. METRIC без метаданных не форматировать автоматически как процент: контракт допускает разные метрики. CNT может быть больше длины APP_IDS: это ограниченная выборка, подпиши «показано N из CNT». Если полного списка сервер не предоставляет, не обещать переход ко всем CNT.

**ИИ-мнение и HTML.** Отдельный блок независимого мнения со статусами доступности и ошибки. Это мнение модели, а не доказанная причина и не PASS/FAIL проверки. Кнопки открыть отчёт по ссылке и скачать HTML. HTML формирует сервер; Claude реализует вызов, загрузку и обработку ошибок. Ссылка из скачанного HTML ведёт в приложение и может потребовать входа. При недоступности модели показывать честный статус, не статическую «аналитику» под видом ответа модели.

### 4. Реализация интерфейса

- Русский интерфейс, спокойный аналитический дизайн, читаемые таблицы и явные состояния загрузки, пустого результата, ошибки и недоступности.
- Один API-клиент, адрес API через VITE_API_BASE_URL, без localhost в компонентах. В production допустим тот же origin /api/v1.
- Деморежим через VITE_USE_MOCK_API=true; по умолчанию реальный API. Демо-адаптер изолирован от компонентов и использует те же DTO.
- Не добавляй произвольные UI-библиотеки без необходимости. Зафиксируй зависимости и lock-файл. Предметные вычисления делает сервер; локально допустимы только представление и явно обозначенные учебные фикстуры.
- Клики по сводной должны передавать все ограничения ячейки, включая строку, колонку и глобальные фильтры. Не терять ARRAY_KEY и не кодировать ключ разделением строки по символу |.
- Длинные списки — с пагинацией. Не загружать 290 тысяч строк в браузер и не выводить тысячи APP_IDS в URL.
- Любые строки из JSON, кода, диагностик и ИИ отображать как текст, без выполнения HTML. Ключ API модели в браузер не передавать.
- При ошибке 401 вернуть к входу; при 409 показать, что результат ещё не готов; при 422 — ошибки формы. Ошибки сети не превращать в нулевые успешные итоги.
- Показать время обновления и источник данных. Для индикаторов различать «нет данных» и 0.

### 6. Критерии готовности твоей части

1. Frontend устанавливается и запускается по README; build и проверка TypeScript проходят.
2. Есть полностью проходящий сценарий: конфигурация → запуск → журнал и код → сводка → сводная → заявка → атрибут → отчёт проверок → новая проверка → HTML.
3. Новая проверка в редакторе действительно отправляется на сервер. В деморежиме это только имитация, подписанная как таковая; демо не подтверждает интеграцию.
4. Проверены SAME / VALUE_CHANGED / ATTRIBUTE_NEW / ATTRIBUTE_LOST; LOW/HIGH; длинные значения; null, false, 0 и отсутствие; CNT больше APP_IDS.length; ошибка выполнения Python; недоступная модель.
5. Есть минимум несколько содержательных браузерных проверок: изменение раскладки меняет запрос; клик по ячейке сохраняет фильтр; переход к атрибуту; добавление проверки обновляет отчёт; ошибка не показывается как успешный ноль. Покрой их доступным инструментом и укажи, что реально запускал.
6. Проверка с реальным сервером и двумя пользователями отмечена отдельно от mock-проверок. Если backend ещё недоступен, перечисли непроверенные пункты.
7. Сдан список изменённых файлов, команды запуска/сборки/проверок, результат, блокировки и готовность к объединению. При наличии Git — коммит/ветка, без самостоятельного merge в main.

### 7. Что делает Codex, не дублировать

Codex реализует вход и проверку владельца объектов на сервере, регистрацию датасетов, доступ к samples, хранение конфигураций, worker, безопасное исполнение Python, адаптер MartAPI для пяти проверок, индексы, факты и точный drill-down, HTML-экспорт, модельный адаптер, измерения и окончательную интеграцию. UI не является границей безопасности. Не реализуй запасной backend и не правь выданные проверки ради красивого отчёта.
