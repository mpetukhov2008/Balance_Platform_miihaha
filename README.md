**Задача Balance Platform:** сравнение ответов двух версий системы принятия решений, конфигурируемые Python-процедуры и проверки, сводная таблица с детализацией и HTML-отчёт с независимым мнением ИИ.

Финальная ветка — [`main`](https://github.com/mpetukhov2008/Balance_Platform_miihaha/tree/main). 

## 1. Решение и функциональность

Приложение сравнивает JSON-ответы BEFORE (MASTER) и AFTER (BETA), сохраняет результаты и позволяет исследовать изменения от общих показателей до конкретного значения атрибута. Четыре типа: `SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`. Отсутствие атрибута, `null`, `false`, `0` и пустая строка различаются.

Реализованы конфигурации датасета и процедур, журнал этапов, сводка, изменение раскладки и фильтров сводной, переход ячейка → заявки → заявка → атрибут, пять проверок организаторов, создание и применение своей Python-проверки без повторного полного прогона, HTML-экспорт и мнение YandexGPT. Состояние сохраняется на сервере после перезагрузки страницы. У каждого пользователя свои конфигурации, скрипты и запуски.

![Сводка полного прогона в проверенной установке](docs/images/scenario-summary.jpg)

На скриншоте добавлены две пользовательские проверки: 34 строки, ревизия 4. Базовый отчёт пяти проверок организаторов содержит 32 строки.

## 2. Запуск на чистой машине

### Локальный запуск на Windows PowerShell

Нужны Git, Python **3.12** с `pip`/`venv`, Node.js **24 LTS** с npm. Допустим Node.js 20.19+ или 22.12+; проверенная версия — 24.22.1. Для локальной демонстрации с проверенным кодом Docker не нужен.

Перед установкой проверьте версии установленных на компьютере программ: `python --version`, `node --version` и `npm --version`. Если команда `python` указывает на другую версию, вместо `python -m venv .venv` используйте `py -3.12 -m venv .venv`.

**Для участников команды:** войдите в GitHub аккаунтом с доступом к репозиторию и скачайте **`team-local.env`** из [закрытого командного релиза](https://github.com/mpetukhov2008/Balance_Platform_miihaha/releases/tag/team-local-config-20261107). В нём уже есть рабочий ключ Yandex, ID каталога, настройки адресов и пароль локального PostgreSQL. Сам файл не входит в коммиты. Если релиз возвращает 404, проверьте вход и запросите у владельца доступ к репозиторию.

Если файл скачан в другую папку, подставьте его фактический путь в команду копирования. На полный прогон требуется место для БД порядка 1 ГБ; повторные прогоны увеличивают расход диска.

**Команды ниже выполняются в PowerShell. Командная строка Windows (`cmd.exe`) для этой инструкции не подойдёт.** После клонирования и перехода в папку проекта выполняйте остальные команды из его корня.

```powershell
git clone --branch main https://github.com/mpetukhov2008/Balance_Platform_miihaha.git
Set-Location Balance_Platform_miihaha
# Если скачали командный файл в стандартную папку загрузок:
Copy-Item "$env:USERPROFILE\Downloads\team-local.env" .env
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
npm --prefix frontend ci
npm --prefix frontend run build
.\.venv\Scripts\python.exe -m backend.manage create-user analyst
.\.venv\Scripts\python.exe -m backend.manage create-user analyst2
```

Если при выполнении `npm --prefix frontend ci` PowerShell блокирует `npm.ps1` с сообщением о запрете выполнения скриптов, в том же окне выполните:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope Process
npm --prefix frontend ci
```

При запросе подтверждения подтвердите изменение политики. Оно действует только до закрытия текущего сеанса PowerShell. После успешного повторного выполнения `npm --prefix frontend ci` продолжите с `npm --prefix frontend run build` и оставшихся команд выше.

Каждая команда создания пользователя запрашивает пароль интерактивно (минимум 10 символов). Пользователей и паролей по умолчанию нет. Второй аккаунт нужен для проверки разделения данных.

Без доступа к командному ключу пропустите копирование `.env`: численная обработка работает, но ИИ покажет отсутствие настроек. Если `.env` уже существует, сначала сохраните свою копию, чтобы не потерять её настройки.

Терминал 1 — API и собранный интерфейс:

```powershell
$env:APP_PUBLIC_URL='http://localhost:8000'
.\.venv\Scripts\python.exe -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Терминал 2 — из того же корня проекта запустить **один** worker:

```powershell
$env:EXECUTION_MODE='trusted-local'
.\.venv\Scripts\python.exe -m backend.worker
```

Откройте **[http://localhost:8000](http://localhost:8000)** и войдите созданным аккаунтом. Проверка API: [http://localhost:8000/api/v1/health](http://localhost:8000/api/v1/health), документация API: [http://localhost:8000/docs](http://localhost:8000/docs). Для расчётов должны работать оба терминала; без worker запуск остаётся в очереди. Метаданные и результаты находятся в локальном `runtime/balance.db`, создаваемом автоматически.

`trusted-local` исполняет Python с правами пользователя компьютера и предназначен для проверенного кода локальной демонстрации. Для исполнения чужого кода нужен контейнерный режим ниже. Автоматического перехода из Docker в `trusted-local` нет.

### PostgreSQL и Docker Compose

Нужен работающий Docker Engine с Linux-контейнерами и Compose. Python и Node.js на хосте для этого варианта не требуются. Из корня проекта в PowerShell:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# Если использован .env.example, замените POSTGRES_PASSWORD на случайный URL-safe пароль.
docker compose --profile tools build
docker compose up -d db api worker backups
docker compose exec api python -m backend.manage create-user analyst
docker compose exec api python -m backend.manage create-user analyst2
```

В Linux/macOS вместо первой команды: `test -f .env || cp .env.example .env`. Затем используйте те же команды Docker. В `.env.example` уже задан путь к включённому полному датасету. При собственных данных задайте `DATA_DIR` папкой, содержащей `BEFORE_MASTER/` и `AFTER_BETA/`; после изменения пересоздайте сервисы командой `docker compose up -d --force-recreate api worker`.

Интерфейс доступен по **http://localhost:8000**, PostgreSQL хранит данные в именованном томе `postgres-data`. Диагностика: `docker compose ps`, `docker compose logs --tail 100 api worker`. Остановка с сохранением данных: `docker compose down`. Не добавляйте `-v`, если хотите сохранить пользователей и отчёты.

Worker использует Docker daemon и запускает runner без сети, host mounts и прав root, с read-only root, ограничениями CPU/памяти/PID и времени. API-контейнер не получает Docker socket. Запускайте один worker: автоматического продолжения прерванной процедуры нет, после перезапуска незавершённая работа отмечается FAILED и требует нового запуска.

Лимит одной процедуры по умолчанию — 180 секунд (`SCRIPT_TIMEOUT`), память runner — 2 ГБ, вывод — 512 МиБ. Это конечные ограничения; большой набор на медленном компьютере может потребовать отдельной настройки и повторной проверки.

### Настройка ИИ

Для реального мнения нужен собственный доступ к Yandex AI Studio, права генерации и биллинг. Создайте или дополните исключённый из Git файл `.env` в корне:

```dotenv
AI_PROVIDER=yandex
AI_FOLDER_ID=идентификатор_каталога
AI_API_KEY=секретный_ключ
```

Worker читает простые `KEY=value` из `.env`, переменные окружения процесса имеют приоритет. В Compose значения передаются из `.env`. Перезапустите worker после изменения ключа. Модель по умолчанию: `gpt://<AI_FOLDER_ID>/yandexgpt-5.1`; отдельные `AI_API_URL` и `AI_MODEL` для Yandex не нужны. При недоступном ИИ вычисленный отчёт остаётся доступен, статус и ошибка показываются в разделе «ИИ и HTML».

Командный файл из закрытого релиза уже содержит эти три настройки. Адрес API — `https://ai.api.cloud.yandex.net/v1/chat/completions`, авторизация — `Api-Key`; приложение настраивает их автоматически. Файл содержит рабочий доступ к платному API: не добавляйте его в Git и не пересылайте публично. Исключённый из Git `.env` должен лежать рядом с `compose.yaml`, а не в `frontend/` или `backend/`.

Секрет `AI_API_KEY` в GitHub Actions **не переносится автоматически** в клонированный проект или локальный `.env`. Для локальной команды используется файл из релиза, а Actions-secret предназначен для настроенных workflow. Рабочие ключи не включены в исходный код. Для другого OpenAI-compatible провайдера задайте `AI_PROVIDER=openai-compatible`, полный `AI_API_URL` до `chat/completions`, `AI_MODEL` и `AI_API_KEY`.

## 3. Данные

### Загрузка своего датасета через сайт

В разделе **«Конфигурации» → «Загрузить датасет»** (или при редактировании конфигурации) укажите название и выберите ZIP-архив. Нажмите **«Загрузить датасет»**: сервер проверит файлы, сохранит набор и автоматически выберет его для конфигурации. Затем нажмите **«Сохранить и запустить»**. В новую конфигурацию также нужно ввести её название.

Архив должен содержать две папки с JSON-файлами в UTF-8; допускается общая родительская папка:

| Версия | Имя папки | Пример файла |
|---|---|---|
| До изменения | `BEFORE` или `BEFORE_MASTER` | `BEFORE/application-001.json` |
| После изменения | `AFTER` или `AFTER_BETA` | `AFTER/application-001.json` |

Для каждой заявки нужны обе версии с одинаковыми именами файлов. В обоих JSON поле `appData.application_id` должно совпадать с именем файла без `.json`, например `application-001`. Минимальный документ: `{"appData":{"application_id":"application-001"},"decisionResult":{"decision":"APPROVE"}}`. Если данные содержат новые массивы, задайте правила их сопоставления в параметре `arrays` процедуры нормализации.

По умолчанию: ZIP до **32 МиБ**, распакованные данные до **64 МиБ**, один JSON до **8 МиБ**, до **20 000 пар**, до **5 датасетов** и **256 МиБ данных на аккаунт**, до 10 попыток загрузки в час. Интерфейс получает текущие ограничения от сервера. Настройки `MAX_DATASET_*` и `DATASET_UPLOADS_PER_USER_HOUR` описаны в `.env.example` и передаются сервисам Compose.

Датасет доступен только загрузившему его пользователю, включая публичный режим приложения. Файлы сохраняются в SQL-БД, поэтому API и worker видят один набор без общей папки на диске; перезапуск сервисов их не удаляет, резервная копия БД включает эти данные. Повторная загрузка создаёт отдельный набор и не меняет результаты прежних запусков. Невалидный архив не создаёт частичный датасет.

### Встроенные и внешние наборы

Дополнительные внешние данные и обучение собственной модели не использовались. В репозитории находятся исходная постановка, пять проверок, четыре пары `Исходники/samples/{BEFORE,AFTER}` и полный датасет: **2 002 пары**, `Исходники/data/RUN-20260827-0001/RESULTS/{BEFORE_MASTER,AFTER_BETA}`. При обычном клонировании вручную скачивать их не нужно.

В настройках запуска доступны «Четыре реальные заявки» (`samples`) и «Полный датасет» (`full`). Собственный полный набор можно подключить переменной окружения `FULL_DATA_ROOT` для API и worker при локальном запуске или `DATA_DIR` в Compose. Имена парных файлов и `appData.application_id` должны совпадать; несовпадения вызывают ошибку.

Предобработка преобразует вложенные JSON в строки с `PATH` и `ARRAY_KEY`, сопоставляет элементы массивов по предметным ключам и вычисляет нормализованные значения для сравнения. Скалярные PD_MODEL/CUTOFF берутся у продукта top-offer, а при его отсутствии — у минимального product_id в лексикографическом порядке. Все продукты и их атрибуты при этом остаются в сравнении. Это явная политика прототипа.

## 6. Архитектура и алгоритмы

Браузер обращается к API; API сохраняет конфигурацию и ставит задачу в очередь SQL. Один worker исполняет `NORMALIZE → UNION → COMPARE → AGGREGATE → CHECKS → AI_REVIEW → PUBLISH`. API остаётся доступен во время расчёта; результаты открываются после публикации.

Нормализованные строки, сравнение, разрезы, facts и проверки хранятся в SQL. Сводная агрегируется сервером; `CNT` — сумма участий в группах, которая может превышать число уникальных заявок. `drilldownToken` сохраняет ограничения ячейки для перехода к точному списку заявок и атрибутам. Новая проверка обновляет ревизию общего отчёта без повторной нормализации и перезаписи витрины. Повторное применение той же `CHECK.id` заменяет её строки.

ИИ получает ограниченные агрегаты и результаты проверок, без исходных JSON и `APP_IDS`, с заголовком `x-data-logging-enabled=false` для Yandex. Числа и PASS/FAIL вычисляет код; ИИ предлагает гипотезы и дальнейшие проверки, а не устанавливает причинность. Кнопка «Сформировать мнение» запускает фоновую генерацию. После изменения ревизии прежнее мнение получает статус STALE.

API доступен в `/docs`. Все прикладные пути имеют префикс `/api/v1`; вход — `POST /auth/login`, cookie — HttpOnly. Для POST/PATCH после входа нужен `X-CSRF-Token` из ответа. Браузерный клиент передаёт его автоматически. Запросы и ответы описаны в [контракте API](contracts/API_CONTRACT.md).

## 7. Проверки, эксперименты и результаты

```powershell
.\.venv\Scripts\python.exe -m pytest -q
npm --prefix frontend test
npm --prefix frontend run build
.\.venv\Scripts\python.exe -m backend.validate_dataset --dataset full --trusted-local
```

Последняя команда создаёт отдельную БД и JSON с результатами в `runtime/validation-*`; она не добавляет запуск в учётную запись браузера и не вызывает ИИ. В Linux/macOS замените путь Python на `.venv/bin/python`.

Для проверки уже запущенного API и worker можно выполнить:

```powershell
.\.venv\Scripts\python.exe scripts/verify_scenario.py --username analyst --other-username analyst2 --dataset full
```

Команда запросит пароль первого аккаунта; для второго предполагается тот же пароль, либо задайте ему `SCENARIO_OTHER_PASSWORD` в окружении. Проверка создаёт отдельный прогон и тестовые скрипты в аккаунте, проверяет числа, четыре типа изменений, детализацию, stdout/stderr, добавление и замену проверки, ошибки Python, HTML и закрытость чужого отчёта. Она не вызывает ИИ. Результат — `runtime/scenario-verification.json`. Для повторной проверки существующего прогона добавьте `--run-id <id>`; его отчёт будет дополнен тестовой проверкой. Для другого адреса используйте `--base-url`.

07.11.2026 полный прогон на Windows/Python 3.12.14/SQLite/trusted-local занял **81,42 с**: 2 002 заявки, **502 с различиями**, **385 со сменой решения**, **167 со сменой решения при изменении внешних данных**. Совпадение с закрытым эталоном жюри не подтверждено. До пакетной записи pivot-токенов SQL pivot по PATH занимал 2,18–2,29 с, список изменившихся заявок — 0,50–0,55 с; БД — около 1 ГБ. Подробности: [полный прогон](docs/FULL_DATA_VALIDATION.md), [синтетические SQL-измерения](docs/SQL_BENCHMARK.md).

При повторной проверке из нового venv прошёл 21 серверный тест (2 локальных Docker-теста пропущены), после чистого `npm ci` — 18 UI-тестов и production-сборка. Аудит npm при проверке 07.11.2026 сообщил 0 уязвимостей. GitHub Actions подтвердил frontend, backend, PostgreSQL и Docker runner, а [полный Compose-сценарий](https://github.com/mpetukhov2008/Balance_Platform_miihaha/actions/runs/42407693143) — сборку приложения с нуля и весь HTTP-сценарий на 2002 парах. Проверены числа 2002/502/385/167, четыре типа изменений, drill-down, новая проверка и её замена, stdout/stderr, ошибка Python, HTML и разделение аккаунтов. Реальный YandexGPT-ответ READY получен локально по агрегатам полного прогона, повторно — после изменения ревизии; платный ИИ в Compose CI не вызывается.

Сценарий демонстрации: [девять шагов до 20 минут](docs/DEMO_VIDEO_GUIDE.md). Конфигурация → запуск и журнал → сводка → изменение раскладки → заявка и атрибут → отчёт проверок → создание своей проверки → HTML → объяснение архитектуры. При открытии скачанного HTML переходы возвращают в работающее приложение по `APP_PUBLIC_URL`; после выхода потребуется повторный вход.

Проверка README, пользовательского сценария и критериев жюри: [отчёт приёмки](docs/ACCEPTANCE.md). Workflow `Compose scenario` собирает всё приложение и проверяет полный набор через настоящий API, PostgreSQL и контейнерный worker; он не использует платный ключ ИИ.

### Если запуск не получается

| Симптом | Что проверить |
|---|---|
| GitHub или релиз показывает 404 | Вход в нужный GitHub-аккаунт и доступ к закрытому репозиторию |
| `python`/`npm` не найдены | Установить Python 3.12 и Node.js 24 с npm, затем открыть новый терминал |
| Сайт не открывается | API запущен, терминал не закрыт; адрес `http://localhost:8000` |
| Запуск остаётся «В очереди» | Второй терминал с worker запущен из того же корня проекта; используется та же БД |
| Локально возникает ошибка Docker | Для штатного проверенного кода запустить worker с `EXECUTION_MODE=trusted-local`, как в инструкции |
| ИИ не настроен или возвращает ошибку | `.env` находится в корне, файл не переименован в `.env.txt`; перезапустить worker и проверить права/биллинг Yandex |
| Полный датасет недоступен | Наличие обеих папок с JSON; в Compose `DATA_DIR` должен указывать на `RESULTS`, а не на родительский каталог |
| Ошибка 403 при входе | Открывать `localhost`, как в инструкции; при своём адресе согласовать его с `ALLOWED_ORIGINS` API |
| Порт 8000 занят | Остановить прежний экземпляр или выбрать другой порт, одновременно обновив `APP_PUBLIC_URL` и `ALLOWED_ORIGINS` API |

Не запускайте разные установки на одном hostname одновременно в одном браузерном профиле: cookie сессии общая для портов этого hostname. Для параллельных установок используйте разные профили браузера либо отдельные hostname с соответствующим `ALLOWED_ORIGINS`.

## 8. Ограничения и развитие

Поддерживается один worker; SQLite используется для локального запуска с одним worker, PostgreSQL — для Compose. При обрыве процедуры автоматического resume нет. Скрытый набор и масштаб 20 000 заявок не проверены. UI предупреждает о неполноте после загрузки 10 000 строк проверок/каталогов. ИИ зависит от провайдера и биллинга, при его ошибке численный отчёт сохраняется. Локальный запуск подтверждён на Windows, полный Compose — на Linux в GitHub Actions. Docker Engine этой Windows-машины возвращает HTTP 500; нативный запуск на macOS отдельно не проверялся. Встроенный браузер запрещает file://: скачанный HTML проверен по содержимому, а его веб-версия и обратные ссылки — в браузере.

Для самостоятельного доступа реализованы регистрация, сохраняемые ограничения запросов и бюджета ИИ, ограничение очереди и дополнительные проверки Docker-runner. По умолчанию регистрация выключена; публичный режим требует PostgreSQL, Docker, HTTPS и secure cookie. Сервис `backups` делает ежедневные копии PostgreSQL; для SQLite есть команды создания и восстановления. Подробные настройки, лимиты, команды восстановления и границы защиты: [PUBLIC_ACCESS.md](docs/PUBLIC_ACCESS.md). Это не автоматическое размещение в интернете: домен, HTTPS proxy, выделенный сервер, мониторинг диска и внешнее защищённое хранилище копий настраивает владелец. Дальнейшее развитие: масштабирование очереди, продолжение прерванных задач, очистка старых результатов и проверка качества гипотез ИИ.

Для сдачи остаются видео до 20 минут, его ссылка в README, доступ экспертов к репозиторию и отправка [формы организаторов](https://forms.yandex.ru/u/6aedea5f6f1ca49998bfe6e7/) **до 8 ноября, 09:30 МСК**. После Stop Coding изменять решение и репозиторий нельзя.

## 10. Безопасность и окончательная проверка

[Отчёт проверки безопасности](docs/SECURITY_REVIEW.md) описывает выявленные проблемы, исправления, зависимости и границы проверки. Усилены ранняя авторизация ZIP, ограничения параллельных загрузок, обработка некорректного CSRF, права API-контейнера и доступ к ключам ИИ. Ключ получает только worker. API работает от UID 65534 с read-only root и без Docker socket/CLI. Обновлён pytest с 9.0.2 до 9.0.3; npm audit и pip-audit повторяются в CI Security.

Тесты включают владение объектами и HTML, CSRF/Origin, ошибки Python, четыре типа изменений, загрузку и сохранность личных данных, SQL-детализацию, квоты, Docker-изоляцию и восстановление backup. Полный Compose-сценарий собирает приложение с нуля, проверяет личный ZIP, затем 2002 пары и восстановление отдельной БД. Проверка не является гарантией отсутствия неизвестных атак и не заменяет аудит внешнего хостинга.

Подробная политика сообщений об уязвимостях: [SECURITY.md](SECURITY.md). Для доступа экспертов к приватному репозиторию и размещения настоящего видео требуется действие участника команды до Stop Coding. Ключи, пароли и командный .env не должны попадать в запись или публичные материалы.
