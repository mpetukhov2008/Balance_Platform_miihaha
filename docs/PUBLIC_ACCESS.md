# Самостоятельный доступ, лимиты и восстановление

Эта инструкция относится к контейнерной установке. Она не публикует сервер автоматически: нужны Linux-сервер с Docker, домен, HTTPS reverse proxy и доступ администратора. Локальная демонстрация по основному README остаётся доступной без регистрации.

## Включение регистрации

1. Сделайте резервную копию существующей базы. Не используйте рабочие кредитные данные для открытой демонстрации.
2. Соберите runner и приложение: `docker compose --profile tools build`.
3. Настройте `.env` (вместо `example.org` — свой домен):

```dotenv
APP_PUBLIC_URL=https://example.org
ALLOWED_ORIGINS=https://example.org
COOKIE_SECURE=true
PUBLIC_MODE=true
ALLOW_REGISTRATION=true
# Только разрешённые к публикации датасеты. Пустое значение закрывает все наборы.
PUBLIC_DATASET_IDS=samples
BACKUP_DIR=./runtime/backups/postgres
BACKUP_KEEP=7
```

4. На сервере направьте HTTPS reverse proxy на `127.0.0.1:8000`. Порт приложения в Compose привязан к localhost; не открывайте PostgreSQL и Docker socket в интернет. Proxy должен ограничивать тело запроса до 1 МиБ, длительность загрузки и число соединений.
5. Для корректного IP в ограничениях задайте `FORWARDED_ALLOW_IPS` **точным адресом своего доверенного proxy**, видимым приложению. В Docker это может быть адрес шлюза сети, а не `127.0.0.1`. Не задавайте `*`. Proxy должен заменять входящий `X-Forwarded-For`; иначе разные посетители делят один IP-лимит или могут обходить его. Личный и общий лимиты ИИ от IP не зависят.
6. Запустите `docker compose up -d db api worker backups`. Проверьте `docker compose ps`, `docker compose logs --tail 100 api worker backups`.
7. Через HTTPS откройте «Создать аккаунт», зарегистрируйтесь и войдите. Логин: 3–40 латинских букв, цифр, `.`, `_`, `-`, без учёта регистра. Пароль: 15–128 символов. Подтверждение пароля проверяет интерфейс. Подтверждения почты и восстановления забытого пароля сейчас нет; это задача администратора.
8. Создайте два аккаунта: конфигурации, скрипты, запуски и отчёты одного не должны быть доступны второму. Доступ к каталогу опубликованных исходных данных одинаковый для всех зарегистрированных пользователей.

`PUBLIC_MODE` не запустится без PostgreSQL, Docker, HTTPS-адресов и secure cookie. При включении регистрации база сохраняет обязательность Docker: случайный запуск worker в `trusted-local` с этой базой завершится ошибкой даже после выключения регистрации. Это преднамеренная защита. Не удаляйте запись политики, чтобы обойти её.

Для проверки регистрации на собственном компьютере достаточно контейнерного Compose с `ALLOW_REGISTRATION=true` и `PUBLIC_MODE=false`; HTTP допускается только для такой закрытой локальной проверки. Регистрация в `trusted-local` запрещена.

## Лимиты по умолчанию

| Ограничение | Значение | Переменная |
|---|---:|---|
| API с одного IP | 600/мин | `API_REQUESTS_PER_MINUTE` |
| API одного аккаунта | 600/мин | `USER_REQUESTS_PER_MINUTE` |
| Попытки входа с IP | 20/15 мин | `LOGIN_ATTEMPTS_PER_15_MIN` |
| Попытки входа со всех IP | 60/мин | `LOGIN_ATTEMPTS_GLOBAL_PER_MIN` |
| Попытки регистрации с IP | 3/час | `REGISTRATIONS_PER_IP_HOUR` |
| Попытки регистрации всего | 100/день | `REGISTRATIONS_PER_DAY` |
| Вычислительные задачи пользователя | 30/час | `COMPUTE_JOBS_PER_USER_HOUR` |
| Задачи в очереди и в работе | 2 на пользователя, 50 всего | `MAX_PENDING_JOBS_PER_USER`, `MAX_PENDING_JOBS` |
| Сохранённые полные запуски | 10 на пользователя | `MAX_RUNS_PER_USER` |
| Запросы ИИ | 10 на пользователя, 50 всего/день | `AI_REQUESTS_PER_USER_DAY`, `AI_REQUESTS_GLOBAL_DAY` |
| Токены ИИ, вход + выход | 30 000 на пользователя, 200 000 всего/день | `AI_TOKENS_PER_USER_DAY`, `AI_TOKENS_GLOBAL_DAY` |
| Максимальный ответ ИИ | 1 500 токенов | `AI_MAX_OUTPUT_TOKENS` |

Счётчики хранятся в БД и атомарно обновляются между процессами. Перезапуск их не сбрасывает. Окна привязаны к UTC, суточные — к 00:00 UTC (03:00 МСК), а не к скользящим 24 часам. На границе окон возможен двойной расход относительно одного окна. `0` закрывает соответствующий бюджет. HTTP 429 содержит `Retry-After`. Неудачные попытки входа и регистрации также расходуют соответствующий лимит.

Первичная генерация мнения и повторная генерация используют одни и те же лимиты. Перед запросом резервируются верхняя оценка входных токенов по UTF-8-байтам с запасом и максимальный выход. Если провайдер сообщает корректный `usage.total_tokens`, разница возвращается в оба токенных бюджета. При таймауте, ошибке, отсутствии usage резерв остаётся списанным; автоматических повторов нет. Поэтому показанное потребление может быть консервативнее фактического счёта провайдера. В интерфейсе раздела ИИ виден личный остаток бюджета.

Это **токенные и количественные ограничения, не точный рублёвый баланс**. Стоимость зависит от выбранной модели и тарифа. Настройте отдельный ключ, квоты и уведомления в кабинете провайдера. Общий счётчик приложения не учитывает использование этого же ключа в других программах и не защищает от изменений тарифа провайдера. Восстановление старой базы также откатывает счётчики: после аварии сначала отключите ИИ, проверьте потребление у провайдера и только затем включайте его.

## Проверки исполнения Python

Пользовательский код выполняется в отдельном runner без сети, Docker socket, каталогов хоста и ключей ИИ. Включены read-only root, непривилегированный UID 65534, сброс capabilities, no-new-privileges, стандартный Docker seccomp, отдельный IPC, init, ограничения CPU, памяти, PID, файловых дескрипторов, времени и вывода. `/tmp` ограничен 32 МиБ и `noexec,nosuid`. Для CHECK вывод ограничен 8 МиБ, число строк 10 000, выборка APP_IDS 200 уникальными существующими заявками; счётчики, перечисления, текст и числовая метрика проверяются до публикации. В конфигурации максимум 20 проверок. Ошибки не превращаются в успешный отчёт.

CI отдельно запускает проверки отсутствия сети и секретов, запрета записи в `/app`, UID/capabilities/no-new-privileges/seccomp и таймаута в реальном Docker. Это инженерные проверки, а не независимый аудит безопасности. Worker имеет доступ к Docker daemon и должен находиться на выделенном хосте; Docker использует ядро хоста. Для массового исполнения враждебного кода рекомендуются отдельные worker-хосты и усиленная изоляция исполнения. Мониторинг свободного диска обязателен: полный запуск занимает порядка 1 ГБ, автоматической очистки результатов пока нет. Администратор управляет сроком хранения и числом пользователей.

## PostgreSQL: копия и восстановление

Сервис `backups` делает `pg_dump` при запуске, затем раз в 24 часа, хранит 7 последних снимков, проверяет читаемость каталога дампа и записывает SHA-256. Каталог — `BACKUP_DIR` на хосте. Ручной снимок:

```bash
docker compose run --rm backups --once
docker compose run --rm --entrypoint sh backups -c 'cd /backups && sha256sum -c *.sha256'
```

Снимки содержат пользовательские данные, хэши паролей, сеансы и квоты. Не публикуйте их и не кладите в GitHub Releases. Ограничьте права каталога, шифруйте диск и настройте отдельное зашифрованное хранилище вне сервера: копия на том же диске не переживёт потерю диска. Удалённое хранилище этим проектом автоматически не создаётся. `.env` храните отдельно в защищённом менеджере секретов: в дамп PostgreSQL он не входит.

Проверяйте восстановление в отдельную базу, не поверх работающей:

```bash
docker compose exec -T db createdb -U balance balance_restore
docker compose run --rm --entrypoint sh backups -c 'pg_restore --exit-on-error --no-owner --no-acl -d balance_restore "$(ls -t /backups/balance-*.dump | head -n 1)"'
docker compose exec -T db psql -U balance -d balance_restore -c 'SELECT kind, count(*) FROM objects GROUP BY kind;'
```

Команда выбирает последний снимок; при реальной аварии выбирайте нужную дату вручную. После проверки остановите API/worker, сделайте ещё одну копию текущего состояния, переключите `DATABASE_URL` обоих сервисов на восстановленную базу и пересоздайте сервисы. SQL-копия сохраняет незавершённые задачи: worker пометит прежние RUNNING как FAILED; исходные датасеты и runner-образ восстанавливаются отдельно. Проверьте вход, последний готовый отчёт и HTML. Замените сеансы и ключи при подозрении на компрометацию. Квоты ИИ после отката сверяйте с провайдером.

## SQLite для локальной демонстрации

В PowerShell замените `python` на `.\.venv\Scripts\python.exe`, если окружение не активировано:

```bash
python -m backend.backup create runtime/balance.db runtime/backups/sqlite --keep 7
python -m backend.backup verify runtime/backups/sqlite/balance-ДАТА.db
python -m backend.backup restore runtime/backups/sqlite/balance-ДАТА.db runtime/restored.db
```

Подставьте фактическое имя, напечатанное командой create. Используется SQLite backup API, включая WAL; простое копирование открытого `.db` не заменяет эту команду. Для автоматизации запускайте create ежедневно через планировщик ОС. После восстановления остановите оба процесса и укажите им `DATABASE_URL=sqlite:///runtime/restored.db`. Существующий файл restore не перезаписывает.
